# Phase 1 — Research Data Foundation

Date: 2026-09-09. This is a repository-reality report, not a trading certification. “Live” below means a real network/terminal read only where the implementation proves one; it does not imply a certified strategy or account.

## 1. Before-state audit

Backtest Lab contained three separate modes. The multi-asset mode initialized 1,200 generated candles per instrument, auto-ran on mount, then independently called `/api/market-data/history`. Single Strategy independently called that endpoint or parsed a CSV. Prop Clearance consumed eligible in-memory feeds/CSV, while its sample-file action generated data. Its execution simulator and `evaluators.ts` are browser research implementations.

The server history endpoint used Binance klines for crypto and Yahoo Finance chart data for forex/metals. Standalone research scripts duplicated those downloads. No browser candle database existed. `localStorage` held presets, adaptive state, UI preferences and several locally represented MT5/cTrader/Visual Bridge account or telemetry records, but bulk research candles were held only in React memory.

The MT5 agent already made genuine terminal calls: login/account/order/position reads, broker symbol discovery, recent `copy_rates_from_pos` market bars, execution, and publication of a small scanner window. It did not accept an explicit candle date range. “History” in its state sync meant account deals, not price bars. The browser communicated with the cloud MT5 bridge/account functions; the separate Visual Bridge probes localhost port 8089, but that is not the MT5 historical path.

## 3. Historical-data paths found

1. `server.ts` `/api/market-data/history`: Binance public klines for crypto; Yahoo chart API for forex/metals.
2. Backtest multi-asset sync and Single Strategy: separate calls to that endpoint, held in component memory.
3. Broker CSV parsers: single and symbol-grouped OHLCV; normalized/sorted, invalid rows discarded.
4. Standalone backtest scripts: direct Binance and Yahoo downloads (duplicate and not production UI services).
5. Scanner edge function: direct Binance spot/futures recent klines for runtime scanning.
6. MT5 market publisher: recent fixed-depth bars from the terminal into `mt5_market_candles`, pruned to 45 days.
7. Core `candles` table: pre-existing backend runtime candle store with retention; it is not expanded here.
8. New canonical path: adapter → validation/normalization → `HistoricalDataService` → IndexedDB.

There was no Yahoo adapter boundary; its automatic use for forex/metals is unsuitable for MT5 certification. The new service never substitutes providers: provider identity is part of the dataset key, and missing MT5 data yields an explicit error.

## 4. MT5 bridge reality

Before: the bridge could register, discover one assigned account, retrieve scoped credentials, heartbeat, claim/ack commands, execute/protect/close orders, sync account state/specs and publish a small recent candle window. It could not request `{symbol,timeframe,from,to}` price history. Deal history was misleadingly adjacent but is not candle history.

Now: `FETCH_HISTORY` is an explicitly read-only command. Payload version `1.0` contains canonical `symbol`, optional `source_symbol`, timeframe and ISO UTC bounds. The agent resolves the actual broker symbol (including suffix discovery), calls `MetaTrader5.copy_rates_range`, and returns version/provider/broker/server/canonical symbol/source symbol/timeframe/bounds plus OHLC, tick volume, spread and real volume. It never generates data. The cloud polling allow-list recognizes this read command.

External runtime limitation: the authenticated browser enqueue-and-wait endpoint for a history command does not exist. `MT5BridgeHistoricalAdapter` therefore accepts a typed transport, isolating that exact missing connection rather than pretending it is live. Cached complete requests need no transport and work offline.

## 5. Backtest data flow

Current UI remains unchanged deliberately: synthetic in-memory defaults or direct server endpoint/CSV feed → browser simulation engine/evaluators. New foundation: research context → canonical service → provider-isolated IndexedDB coverage check → only missing ranges through adapter → validation → deterministic upsert → canonical bars. UI and simulation engine migration remains Phase 2 work; therefore source switching can still change dates/bars in the existing UI.

## 6. Prop replay data flow

Current Prop Clearance filters in-memory feeds to Yahoo/Binance/`live_feed`, accepts imported CSV, and runs its own prop replay/signal competition around the browser simulation outputs. Intended: it receives dataset keys and canonical bars from the same shared context/service as every other mode. `SharedResearchContext` now defines that contract, but Prop Clearance has not been broadly redesigned or rewired.

## 7. Strategy parity findings

Parity is **not established**. Backtests use `src/pages/admin/backtest/evaluators.ts` and `simulationEngine.ts`; scanner/live runtime uses edge-function professional/forex production strategies, indicator engine, arbitrator, risk and execution/account-brain modules. Preset deployment copies configuration toward “live” state but does not make these the same evaluator implementation. Thus Backtest is currently a second trading brain. Phase 1 adds no strategy code and does not claim backtest/live equivalence.

## 8. Implemented architecture

- `types.ts`: canonical candle, request, dataset, coverage, quality, metadata, provider and shared research-context contracts.
- `validation.ts`: deterministic sort/deduplication, OHLC/finite/timestamp rejection, missing interval detection, range merge, staleness and scoring.
- `cache.ts`: IndexedDB v1 (`bars`, `datasets`) plus deterministic memory test double.
- `adapters.ts`: MT5 bridge contract, Binance, Bybit and CSV adapters.
- `HistoricalDataService.ts`: provider registry, cache-first retrieval, missing-only fetch, refresh/delete/coverage/verification and actionable failure.
- MT5 Python agent and bridge allow-list: actual terminal range extraction contract.

No new backtest engine, strategy, production cron, deployment, Supabase table or fake response was added.

## 9. Browser cache architecture

Database `hashibot-historical-v1` stores bars separately from dataset metadata. Dataset identity encodes provider, environment, broker, server, canonical symbol, source/broker symbol and timeframe. Bar primary key is `datasetKey|timestamp`; the unique compound index `[datasetKey,timestamp]` supports bounded range reads and idempotent `put`. Metadata records requested/actual range, counts, UTC, last sync, quality and schema version.

Multi-year M5 bars are records in IndexedDB rather than serialized localStorage blobs, so reads are range bounded and writes do not rewrite an entire dataset. Provider/symbol/timeframe isolation is structural. A production follow-up should benchmark browser quotas and implement chunked transactions/eviction for very large universes.

## 10. MT5 historical sync

Service checks exact timestamps in IndexedDB and derives contiguous missing ranges at timeframe spacing. It invokes the MT5 transport only for those ranges. Valid bars are normalized to UTC epoch milliseconds and upserted. MT5 provenance is `BROKER_VALIDATED`, never automatically `CERTIFICATION`. Complete cached periods return identically while offline. Incomplete/offline requests throw `HistoricalDataUnavailableError` with requested, cached and missing ranges plus bridge/terminal status fields; there is no Yahoo fallback.

## 11. Crypto historical sync

Binance spot klines and Bybit V5 linear klines normalize through the same adapter result and cache/service contract. Existing scanner and execution clients remain untouched. Pagination beyond a provider's 1,000-bar response is a known gap: the service range contract is ready, but adapters need page iteration before UI adoption for multi-year requests.

## 13. Remaining risks

1. Existing Backtest/Prop UIs do not yet consume the service or a persisted shared context.
2. No browser-accessible command enqueue/result wait transport connects the typed MT5 adapter to the cloud queue.
3. MT5 terminal integration requires verification on Windows against multiple broker suffixes, timezones and maximum range behavior.
4. Binance/Bybit adapters need pagination, rate-limit/backoff and final-open-candle exclusion policy.
5. Expected missing intervals currently treat market closures as gaps; an instrument session calendar is needed before quality scoring can certify FX/metals.
6. IndexedDB upgrade/recovery, quota telemetry, chunking and eviction are not implemented.
7. CSV aliases collapse tick/real volume to one volume value; richer CSV columns/provenance remain.
8. Quality scoring is foundational, not a certification rubric; `CERTIFICATION` requires explicit later promotion evidence.
9. Backtest/live strategy evaluators diverge materially.
10. Existing Supabase candle stores remain duplicated runtime paths and must not become the browser research warehouse.

## 14. Next recommended phase

Phase 2 should wire a secured, read-only browser history-command enqueue/status endpoint to the existing MT5 queue, then migrate Backtest Lab and Prop Clearance selection into one persisted `SharedResearchContext` and consume only canonical service datasets. Add provider pagination/session calendars and connected-terminal integration tests. Before accepting performance claims, inventory and converge evaluator/arbitrator/risk/trade-management dependencies so replay invokes the same canonical decision core as scanner/live runtime—without creating another engine.
