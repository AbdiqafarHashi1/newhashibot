# HashiBot Capability Ledger — Phase 11 Baseline

**Audit date:** 2026-07-31  
**Scope:** HashiBot demo runtime only; customer functionality is outside current scope.  
**Runtime owner:** Supabase Edge Functions remain the sole production owners. Google Cloud owns zero responsibilities.

## 1. Audit method and completeness rule

The ledger inventories every deployed handler under `supabase/functions/*/index.ts`, every business-capability family under `supabase/functions/_shared`, the MT5 agent boundary, runtime/trade-management libraries under `src/lib`, Telegram actions, provider mutations, recovery paths, and Operations Center commands. A capability is not considered extracted merely because an interface exists: the **implementation status** column distinguishes canonical reusable logic, portable contracts, and handler-bound orchestration.

Common conventions used below:

- **Reads/writes** name Supabase truth families rather than implying a schema change.
- **Retries** are bounded handler/provider retries already present or `none`; Phase 11 adds none to production.
- **Idempotency** records the current guard (action/event ID, run claim, execution scope, provider client ID, delivery ledger, lifecycle/version guard, or transactional RPC).
- **Monitoring** includes scanner runs, provider/runtime status, heartbeats, execution events, audit/operator events, and safe errors.
- **OC** means Operations Center visibility/actionability.

## 5. Completeness reconciliation

- **17/17 Edge Function entry points** are individually listed in Section 2.
- **All `_shared` capability families** are accounted for in Section 3, including strategy, risk, capital, execution, protection, provider, MT5, Telegram, certification, content, and runtime-proof helpers.

- Handler-bound database/provider/Telegram orchestration is intentionally not copied. Pure canonical implementations are exposed by the portable core; impure work is represented by ports and remains owned by current handlers.
