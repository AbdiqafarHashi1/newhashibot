Every transition has its own source classification in the audit. Unresolved candidates remain unresolved.

Repeated seeds can overwrite existing configuration, pricing, entitlements or runtime switches even with ON CONFLICT. Review each pending seed/update against a protected backup; never replay already-applied migrations to “make schemas match.”

## Reproducible isolated rehearsal

Use Node 24, Docker, `curl` and sufficient disk space. Bootstrap packages/images may require network access; rehearsal containers use an internal network with no published ports. The runner requires cached GoTrue `v2.197.0`; bootstrap it explicitly if absent. Extension sources are pinned and SHA-256 checked: pg_cron tag `v1.6.7` (SQL extension version `1.6`) pg_net `v0.14.0`, and real Supabase Vault `v0.3.1` (archive SHA-256 `344edb590e574cc94937d5665f696b4b04c3af5ae9431cc9050da657ab563b11`).

```bash
docker pull ghcr.io/supabase/gotrue:v2.197.0
bash scripts/phase-p/build-rehearsal.sh
npm run rehearse:deployment
# Explicit compatibility/bootstrap procedure; all 175 files execute in order:
npm run rehearse:deployment -- deployment-compatibility-v1
```

The compact image uses PostgreSQL 15.19; actual GoTrue migrations create Auth tables. Standard Auth helper SQL/roles are explicit platform bootstrap, not application prerequisite fixtures. Install pgcrypto in the `extensions` schema, with `public,extensions` in the database search path, and real Vault before application SQL. GoTrue is removed after its migrations complete to reduce VFS peak disk usage. The harness requires an owned disposable-container label, fresh public schema and internal/disabled network. `cron.launch_active_jobs=off` is set and checked before every file; original cron registrations may create active-definition rows, but the launcher cannot execute them. No external endpoints are called. Each file is transactional; the first error stops execution, without skipping or marking history. Owned containers, their anonymous volumes and networks are removed afterwards.

Results: unchanged chain **BLOCKED** at 020, after 19 files, with exact error `column "active_timeframes" is of type text[] but expression is of type jsonb`. The explicit compatibility chain is **PASSED**, all **175 files**, with real pg_cron, pg_net, Vault and Auth, completed-chain database invariants and read-only catalog capture. Each repair was followed by a fresh full-order attempt until no SQL failure remained. Exact intermediate errors and final source/execution hashes are in the evidence JSON. Untouched-chain failure is retained; success applies to the documented compatible execution, not raw historical replay.

Initial Alpine package downloads returned HTTP 403. The first Debian build exhausted disk during initdb. The final build also disables the redundant package-created PostgreSQL cluster to reduce peak disk usage and restores the native CA bundle after temporary build trust. A Vault-enabled attempt also exhausted disk; removing the owned Auth service after schema bootstrap resolved that peak. These environment limitations were overcome. The connected project reports PostgreSQL 17.6.1.127; this real PostgreSQL 15 rehearsal does not establish hosted version/extension parity. Real Vault is installed but credential operations and a complete Storage service rehearsal remain unverified.

`npm run test:phase-p-db` is a separate prerequisite-fixture test: actual L/M/P SQL, concurrent claims, idempotency, quotas, cancellation/fencing/native completion and RLS/grants. Its explicit Storage/Vault metadata fixtures verify optional-catalog capture, view fingerprints and exclusion of a sentinel secret value. It does **not** establish full migration-chain success.

## One procedure for clean installation and existing-project upgrade

The manifest is the dependency/order authority. [Compatibility source](../../scripts/phase-p/compatibility.mjs) is the per-file exception list; it binds original bytes and expected schema types. [Rehearsal evidence](rehearsal-results.json) records the executed hashes. Neither the preparer nor runner writes migration history. Do not use `db push`, `reset`, `migration repair`, recursive SQL execution, or a combined replacement script.

1. **Common preparation:** pin the reviewed commit and source fingerprint; verify backup/restore and project binding; preserve all existing files and cron definitions. Install the platform prerequisites above. Keep the cron launcher disabled and network isolated during rehearsal. On hosted Supabase, do not run scheduling migrations until an independently reviewed maintenance plan prevents jobs from executing; metadata `active=true` is distinct from actual launcher execution.
2. **Clean database:** build the disposable image and run `npm run rehearse:deployment -- deployment-compatibility-v1`. It starts with an empty public schema and follows all original identities once, in order, transactionally. For reviewable per-file SQL, use `node scripts/phase-p/prepare-compatible-chain.mjs work/phase-p/clean-reviewed-chain` (new ignored directory required). This creates 175 separate files plus a source/execution ledger and performs no database operation. Apply only through a separately authorized, reviewed per-file release, with the same preconditions and extension layout. Never claim that executing compatibility bytes means the original stored statements match; reconcile actual executed content explicitly.
3. **Existing project:** begin with read-only history/content/schema/function/cron inspection below. Reproduce its actual prefix and data in a disposable restore. If history is ambiguous, non-prefix, name-only, or contains an unrecognized definition, STOP. Do not replay an already-applied 020/038/046/050 or overwrite history to match repository names. In particular, never drop an already-correct JSONB reset RPC and never invoke the reset. Inspect its signature and grants instead.
4. **Upgrade repair selection:** if a defective historical file is genuinely pending and blocks later forward SQL, use only its reviewed hash-bound compatibility transaction at that exact position. If that file is already applied, compare its resulting schema/body/grants; create a distinct forward corrective migration only for a proven residual mismatch, after the observed latest identity, and rehearse it on the restored prefix. Do not replay historical seeds to obtain a forward repair. An inaccessible project supplies no evidence for choosing such a correction, so no speculative upgrade SQL is automatically included here.
5. **Populated-data gates:** run [aggregate read-only preflight](upgrade-data-preflight.sql) only after schema inspection confirms its columns exist. Multiple quarantine rows per provider/symbol block 097b's narrower unique index; duplicate non-null execution-order truth rows block 088's unique constraint. STOP with counts, preserve every row and constraint, and resolve the canonical identity contract in a separately reviewed forward correction; never deduplicate by deletion. Unowned legacy rows require the existing ownership-adoption classification, not guessed customer/account assignments. The clean-chain pass does not waive these upgrade gates.
6. **Database batches and verification:** follow all 104 manifest batches, preserving original timestamp order. Check applied content, columns/defaults, constraints, RLS/policies, grants, RPC signatures, invoker views and triggers after each transactional batch. For 088, retain the original composite key/checks and derive new direction/quantity only from existing side/qty; `unknown` status means absent evidence. Later account-ownership SQL retains sole authority to replace its key. Provider compatibility retains canonical `provider_name`; the catch-up index uses a stored read-only alias and nullable unclassified subsystem, not a second execution authority.
7. **Function/configuration order:** database prerequisites and their verification come first. Use `features[].edgeFunctions` and each function's `dependencies`, `rpcs`, `configuration`, JWT setting and closure hash to deploy only the reviewed matching set in a separately authorized release. Stage backend writers/monitors and account/command endpoints after their tables/RPCs, and scanner/publication/orchestration callers after all their database and called-endpoint dependencies. `_shared` modules ship in each function closure, never as independent functions. Deployment-tooling only: no function is deployed in this PR.
8. **Configuration/secrets:** provision only the names recorded per feature/function in the manifest, through protected project configuration. These include Supabase URL/service-role configuration, provider-specific sandbox credentials, MT5 bridge credentials/identity, cron tokens/GUC/Vault references, payment-provider configuration, Telegram bot/chat/destination configuration and any agent-provider configuration. Validate JWT/custom-header contracts without logging values. Do not infer readiness from a secret name or retrieve decrypted secrets. Keep payment, delivery, agent, execution, cloud-worker and scanner activation gates unchanged.
9. **Cron and recovery:** preserve source inventory and inspect actual jobs before any activation. Verify one scanner, target project/current endpoint, header/JWT contract, function version, token presence and all Phase D/E/F/G gates. Stop at the first SQL or fingerprint mismatch; roll back that transaction, retain error/source/executed hash and restore from the tested backup if a committed batch requires recovery. Do not mark failed files applied. Keep scheduling and workers disabled; cron activation remains a separate later release decision.

Additional confirmed clean-order repairs are additive 088 columns (075 already owns the table), the 092 `open_time` index, the precise 097 23-argument revoke, 097 catch-up index/RPC prerequisites, 102's absent boolean flag, appended-column replacements for Phase H/M/O views, and parenthesized Phase-N scalar CASE. The catch-up RPC also requires `occurrence_count`: initialize it from existing `failure_count` only when absent. Its three-argument signature overlaps the older six-argument function defaults. Removing that default requires an exact-signature DROP/recreate without CASCADE in the same transaction. Require original ownership/default ACL, retain both signatures, stored bodies, ACLs and trailing defaults, and refuse custom ownership/grants or dependent objects. Existing Edge callers explicitly pass metadata and remain compatible. Historical six-argument default PUBLIC execution and three-argument authenticated execution are preserved; they differ from later admin-only direct-table policies and require actual ACL/caller review before release. This rehearsal is not a production authorization certification. Actual PostgreSQL verifies the three-argument counter and the metadata-bearing legacy call.

The Phase-N correction changes syntax only: Phase-D/G lineage, provider/environment, ownership, entitlement, advisory lock, idempotency and service-role-only grants remain intact. Platform fixes install real Vault and put pgcrypto in `extensions`; they are not application migrations.
