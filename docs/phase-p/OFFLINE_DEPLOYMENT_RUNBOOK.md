Compatibility is implemented in [compatibility.mjs](../../scripts/phase-p/compatibility.mjs). It requires the exact original file hash, expected occurrence counts and actual column/RPC type. It never edits repository history or migration records. Original and executed hashes are recorded. These early failures occur before a forward migration could run, so the exception is an explicitly selected per-file compatibility path. Online execution/history reconciliation is deliberately not implemented. Already-applied history should receive reviewed forward corrections where feasible, after inspecting its actual schema and callers.

The first three corrections passed real SQL execution, timeframe-value checks, preserved profiles/candles/signals counts and profile RLS; the return-contract correction also passed target-signature and anon/authenticated/service-role grant checks. These are disposable databases, not proof of preservation of actual customer data. The fourth prelude is not fully verified: the following status failure rolls back its entire file. Its absence after failure is checked.

Other overlaps are not reasons to delete files: OR REPLACE bodies are intentional replacements; IF NOT EXISTS catch-up definitions are compatibility behavior that can retain old constraints; reset batching replaces an obsolete overload explicitly; heartbeat index correction replaces a partial index to support the actual upsert target; account onboarding explicitly drops a changed return contract; repeated Phase-O definitions leave the final implementation authoritative. Every transition has its own source classification in the audit. Unresolved candidates remain unresolved.

Repeated seeds can overwrite existing configuration, pricing, entitlements or runtime switches even with ON CONFLICT. Review each pending seed/update against a protected backup; never replay already-applied migrations to “make schemas match.”

## Reproducible isolated rehearsal

Use Node 24, Docker, `curl` and sufficient disk space. Bootstrap packages/images may require network access; rehearsal containers use an internal network with no published ports. The runner requires cached GoTrue `v2.197.0`; bootstrap it explicitly if absent. Extension sources are pinned and SHA-256 checked: pg_cron tag `v1.6.7` (SQL extension version `1.6`) and pg_net `v0.14.0`.

```bash
docker pull ghcr.io/supabase/gotrue:v2.197.0
bash scripts/phase-p/build-rehearsal.sh
npm run rehearse:deployment
# Separate, explicitly modified compatibility experiment:
npm run rehearse:deployment -- deployment-compatibility-v1
```

The compact image uses PostgreSQL 15.19; actual GoTrue migrations create Auth tables. Standard Auth helper SQL/roles are explicit platform bootstrap, not application prerequisite fixtures. The harness requires an owned disposable-container label, fresh public schema and internal/disabled network. `cron.launch_active_jobs=off` is set and checked before every file; original cron registrations may create active-definition rows, but the launcher cannot execute them. No external endpoints are called. Each file is transactional; the first error stops execution, without skipping or marking history. Owned containers, their anonymous volumes and networks are removed afterwards.

Results: unchanged chain **BLOCKED** at 020, after 19 files, with exact error `column "active_timeframes" is of type text[] but expression is of type jsonb`. The separate compatibility run is **BLOCKED** at 050 after 81 completed files, with exact error `new row for relation "execution_provider_controls" violates check constraint "execution_provider_controls_status_check"`. Full stderr/context and transformed-file hashes are in the evidence JSON. Files after those failures have not received full-chain catalog verification.

Initial Alpine package downloads returned HTTP 403. The first Debian build exhausted disk during initdb. Removing only this audit's identified failed build cache and purging compiler dependencies within the build layer allowed the real-extension image to build. The final build also disables the redundant package-created PostgreSQL cluster to reduce peak disk usage and restores the native CA bundle after temporary build trust. These limitations were overcome; the current blocker is repository SQL, not missing pg_cron/pg_net. Hosted PostgreSQL/version/extension parity and a complete Vault/Storage service rehearsal remain unverified.

`npm run test:phase-p-db` is a separate prerequisite-fixture test: actual L/M/P SQL, concurrent claims, idempotency, quotas, cancellation/fencing/native completion and RLS/grants. Its explicit Storage/Vault metadata fixtures verify optional-catalog capture, view fingerprints and exclusion of a sentinel secret value. It does **not** establish full migration-chain success.

## Dry-run and later deployment gates

```bash
npm run plan:deployment -- --observed work/phase-p/online-observed-with-functions.json \
  --reference work/phase-p/reviewed-reference.json \
  --output work/phase-p/deployment-plan.json
```

The reference needs `reviewed: true`, a genuinely PASSED full-chain rehearsal, matching `sourceRef`/`sourceFingerprint`, the verified project/connection binding, `appliedVersions`, a consistent catalog `snapshot`, and reviewed `historyProof` rows binding each stored statement fingerprint to its original source SHA-256. The connection binding includes the project ref and observed schema fingerprint. Reproduce the inspected prefix separately; a full-head snapshot cannot justify prefix drift. Do not set PASSED merely to satisfy this interface.

The planner refuses missing/ambiguous content, unknown/duplicate/non-prefix history, local source changes, incomplete snapshots, schema/RLS/grant/view/RPC drift, platform/extension drift, cron/Vault/Storage metadata drift, unknown deployed source or JWT policy, and an unverified project binding. Refusal emits no pending set. An accepted result is only `REVIEWABLE_DRY_RUN`, with `executionAllowed: false` and `activationAllowed: false`. Prepared SQL is never promoted.

Only after a reviewed plan, tested backup/restore, resolved contradictions and a passing compatible rehearsal: prepare the exact dependency-ordered per-file database batches; verify catalog fingerprints/RPC signatures/RLS/grants/data counts after each batch; then review/deploy the matching Edge functions and configuration in a separately authorized release. Stop on any mismatch. Do not use blind db push, reset, migration repair or a giant replacement SQL script.

Preserve one existing scanner. Scanner/Shadow/reporting, Phase-J membership, Phase-N command consumption and Phase-O agents remain on Supabase. Phase-D risk, Phase-E MT5, Phase-F crypto and Phase-G certification remain canonical. MT5 remains a dedicated Windows feed. Cloud portable workers stay disabled.

Cron activation is a separate final release decision: verify actual target project, current endpoint/auth headers/JWT policy, required GUC/Vault metadata, deployed versions, single-responsibility job identity, scanner certification and each execution/delivery gate. Historical 064/066 URLs and old GUC/header forms are replaced by later rebuilds; proof/test jobs are removed by 068. No missing literal endpoint implementation was found in the source inventory; dynamic targets and actual deployed state remain UNKNOWN. Preserve every existing definition. Prepared consolidation is not automatically authoritative.

Two existing main-triggered Edge deployment workflows are preserved; they can duplicate deployment and resolve project refs differently. Review the release automation before any merge that would trigger it. This audit PR is not merged or deployed.
